## 1. 外部要求逐条核对

### 1.1 DeepSeek 开放平台服务协议 3.2

官方要求开发者对下游系统负责，并与终端用户约定权利义务、规范终端用户行为。来源：[DeepSeek 开放平台服务协议（2026-04-22 更新）](https://cdn.deepseek.com/policies/zh-CN/deepseek-open-platform-terms-of-service.html)。

- 【符合】草案第 1 条规定协议关系和接受方式，第 2、3、5、6 条规定服务、付费、数据和责任，第 4 条列出五类禁止行为，第 4 条末及第 7.2 条规定暂停/终止后果。就协议文本覆盖面而言，已回应 3.2 的“约定双方权利义务、规范使用行为”。
- 【不符合】草案第 1 条的“使用即视为同意”没有实际展示或确认路径。README 的“支持与协议”仅链接源码 LICENSE，没有用户协议入口（`README.md:148-153`）；试用、购买和激活 UI 直接执行动作，没有协议链接、版本、勾选或确认记录（`src/settings/settings-tab.ts:1060-1127`；`src/views/pro-modal.ts:84-170`）。在终端用户实际看不到草案的情况下，不能仅凭文本证明已经完成 3.2 所要求的“约定”。
- 【不符合】草案第 1 条只写“TideLog 开发者/我们”，开发者主体、生效日期仍为空（`docs/TERMS-draft.md:6-16,134-138`）。上线前必须补齐可识别主体和有效联系方式，否则权利义务相对方不明确。

### 1.2 DeepSeek 开放平台服务协议 3.4

官方 3.4 要求审查终端用户输入和输出，并建立关键词表、违法内容特征库、分类模型等风险识别和过滤机制。来源同上。

- 【不符合】草案第 5.5 条只笼统写“必要的合规检查”（`docs/TERMS-draft.md:87-90`），未明确同时覆盖输入与输出，也未说明拦截、处置、申诉、事件记录等基本规则；代码也只有结构/长度校验（`api/src/ai.ts:144-173,443-459`），与 3.4 的具体义务不等量。
- 【承诺但未实现】草案第 5.5 条声称检查会在转发瞬间发生，但服务端仅校验消息结构、输入长度、身份与配额，随后直接调用 DeepSeek（`api/src/ai.ts:144-160,431-488`）。代码中没有关键词表、违法内容特征库、分类模型、moderation API 或任何输入过滤。
- 【承诺但未实现】输出同样没有审查：流式响应字节被直接写回客户端（`api/src/ai.ts:356-428`），非流式响应解析后直接返回（`api/src/ai.ts:509-525`）。当前 BYOK 客户端也直接请求用户所选服务商（`src/ai/ai-provider.ts:18-48`；`src/ai/base-provider.ts:66-101`），不存在 TideLog 合规层。
- 【需律师确认】草案第 5.5 条承诺“不存储、不留档”，但官方协议还要求对涉嫌违法违规/犯罪行为保存相关记录并依法报告。过滤日志与隐私最小化如何兼容，需要律师和安全负责人共同确定留存范围、期限和访问控制。

### 1.3 Obsidian 开发者政策

官方政策要求 README 清楚披露：完整访问需付费、完整访问需账号、网络使用；如存在服务端遥测，还应链接说明数据处理的隐私政策。来源：[Obsidian Developer policies](https://docs.obsidian.md/community-directory/developer-policies)。按本项目给定核查口径，服务端数据收集也必须在 README 披露。

- 【符合】“需付费才能完整使用”已披露：README 列出 Free/Pro 功能差异、价格和购买入口（`README.md:113-133`）。
- 【不符合】“需要账号”未在 README 披露。实际购买 UI 明示需登录/注册爱发电（`src/i18n/zh.ts:763-765`），但 README 购买段落没有该信息（`README.md:129-133`）。
- 【不符合】服务端 AI 数据流和数据收集未正确披露。README 仍称用户配置自己的 API Key、内容发给用户配置的服务商（`README.md:95-102,135-146`），没有披露计划中的 TideLog AI 代理、DeepSeek、`ai_usage`、免费配额锚点和服务端限流记录。对应草案为第 2.2、5.2、5.4、5.6 条；对应服务端代码为 `api/src/ai.ts:176-199,283-305,341-344`、`api/src/index.ts:83-120`。
- 【不符合】README 虽链接 `PRIVACY.md`，但该隐私政策仍称 AI 请求直达用户配置的六类服务商，且 TideLog License 服务“不接收 AI prompts/responses”（`PRIVACY.md:22-28,30-46`），与草案第 2.2、5.2 条和新增代理代码相冲突。

### 1.4 给定产品实际形态

- 【符合】草案第 3.1、3.2 条描述固定时长月卡/年卡且不自动续费，与给定产品方案一致。
- 【承诺但未实现】当前 License API 只接受 `annual` / `lifetime`，年度固定为 365 天，没有月卡类型（`api/src/index.ts:303-322`）；客户端标签也只有“年度版/终身版”（`src/services/license-manager.ts:165-180`），README 仍售卖年度版与终身版（`README.md:113-133`）。草案第 3.1 条的月卡/年卡尚未落地。
- 【符合】草案第 2.2、5.2 条描述用开发者 DeepSeek Key 代用户调用；服务端代理确实从环境变量读取开发者 Key 并请求 DeepSeek（`api/src/index.ts:20-24`；`api/src/ai.ts:176-199`）。
- 【承诺但未实现】上述代理尚未接入插件。插件仍要求用户配置自己的 Key（`src/settings/settings-tab.ts:62-142,447-521`），工厂仍创建 BYOK provider（`src/ai/ai-provider.ts:18-48`），所有主要 AI 调用通过 `plugin.getAIProvider()`（例如 `src/views/chat-controller.ts:179-215`、`src/services/insight-service.ts:89-104`）。因此草案第 2.2、5.2 条描述的当前用户路径不存在。
- 【符合】免费档“今日洞察每月 3 次”的协议数字与服务端常量一致（草案第 2.3 条；`api/src/quota.ts:22-29`）。但由于客户端未接入代理，该配额目前不约束现有 BYOK 调用，详见第 2 节。

## 2. 草案与仓库现状交叉核对

### 2.1 3 台设备上限：草案第 3.3 条

- 【符合】数据库新 License 默认 `max_devices = 3`（`api/schema.sql:3-12`；`api/migration-v2.sql:5-7`）。激活时查询现有设备并按每条 License 的 `row.max_devices` 拒绝超限绑定（`api/src/index.ts:146-218`）。
- 【符合】草案所称 Portal 自助解绑已实现：Portal 查出设备并删除指定绑定（`api/src/index.ts:394-415,418-473`）。
- 结论：当前标准签发路径与“最多 3 台”一致。数据库字段是可变值，因此若运营人员手工修改单个 License 上限，应同步处理其合同例外。

### 2.2 7 天离线宽限：草案第 6.2 条

- 【符合】客户端常量为精确 7 天，`lastVerified` 距今超过 7 天才失去付费权限（`src/services/license-manager.ts:12-13,79-94`）；网络校验失败不清除授权（`src/services/license-manager.ts:222-250`）。
- 【不符合】条款写成泛化的“License 校验失败”，实际并非所有失败都宽限：本地判断发现年度订阅已过期会立即失效（`src/services/license-manager.ts:83-86`），服务端明确返回 `expired` 时也立即把 `activated` 置为 false（`src/services/license-manager.ts:241-245`）。草案第 6.2 条应限定为网络不可达/临时校验失败，并明确宽限不延长订阅到期日、不适用于吊销。

### 2.4 “不存储笔记内容”与实际写库：草案第 5.3、5.4 条

- 【符合】`ai_usage` 只写：随机 id、主体类型、主体 id、功能、周期、创建时间、输入/输出 token 数；不写 messages、prompt、笔记正文或模型输出（`api/migration-v4.sql:5-20`；`api/src/ai.ts:283-305,341-344`）。失败会删除预占记录（`api/src/ai.ts:327-338`）。就 TideLog D1 代码而言，第 5.3 条“不落库笔记正文”属实。
- 【不符合】草案第 5.4 条的“仅记录”清单不完整。实际还存储购买邮箱、订单号（`api/schema.sql:3-12`），Free 配额锚点、周期、使用次数和创建/更新时间（`api/migration-v4.sql:22-33`；`api/src/ai.ts:97-100,258-270`），以及由请求 IP、接口 scope 和时间窗派生的限流哈希、计数和重置时间（`api/src/index.ts:83-120`）。这些均应在第 5.4 条或隐私政策中准确说明。
- 【不符合】草案第 5.2 条说内容先到“我们的服务端”，但当前客户端仍直达用户配置的第三方服务商（`src/ai/base-provider.ts:66-101`）。反过来，新增代理一旦接入，现有 `PRIVACY.md:44` 所称 License 服务“不接收 AI prompts/responses”将变为错误陈述。
- 【需律师确认】代码可证明应用数据库没有正文列，但不能单凭仓库证明 Cloudflare 标准日志或 DeepSeek 侧绝不留存。草案第 5.3 条“请求处理完即丢弃、不留档”和第 5.5 条“不存储、不留档”是否需要限定主体、系统边界和第三方处理规则，需律师确认。

### 2.5 内容合规检查：草案第 5.5 条

- 【承诺但未实现】输入只有类型和大小校验（`api/src/ai.ts:144-173,443-459`），不是内容风险识别。
- 【承诺但未实现】输入在配额预占后原样发送给 DeepSeek（`api/src/ai.ts:474-488`）；输出原样转发（`api/src/ai.ts:356-428,509-525`）。输入、输出两侧均无 3.4 所要求的过滤机制。
- 【承诺但未实现】当前 BYOK 客户端同样没有统一过滤层，直接由各 provider 发出（`src/ai/ai-provider.ts:18-48`；`src/ai/base-provider.ts:66-101`）。因此不能把 DeepSeek 自身可能存在的过滤当作 TideLog 已履行开发者义务。

### 2.6 其他“协议与代码”差异

- 【承诺但未实现】草案第 3.2 条承诺到期前插件内提示。当前代码只在设置页显示到期日（`src/settings/settings-tab.ts:1051-1057`）并在启动时校验（`src/services/license-manager.ts:219-250`），未找到到期前主动提醒逻辑。
- 【承诺但未实现】草案第 1 条将激活、开始试用、使用内置 AI 视为接受协议，但三个入口均无协议展示或确认（`src/settings/settings-tab.ts:1060-1127`；`src/views/pro-modal.ts:84-170`）。
- 【不符合】草案第 9 条只有公开 GitHub Issues，并明确禁止粘贴 License/笔记；`PRIVACY.md:62-64` 却要求用户通过 README 中的“private support request”申请数据删除，而 README 没有私人渠道（`README.md:148-153`）。退款、隐私删除和敏感支持缺少可用入口。

## 3. 中国法下的明显风险点（仅标注需律师确认）

参考资料：[《民法典》第 496、497、506 条](https://www.cac.gov.cn/2020-06/01/c_15925617772683192.htm)、[《消费者权益保护法》第 25、26 条](https://www.samr.gov.cn/zfjcj/tzgg/art/2023/art_615af9ed6bcd4974bf853dd2e02bc663.html)、[《消费者权益保护法实施条例》第 17、19、22 条](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2024/art_0aea188276a44f0baf940ab95ee00e0a.html)、[最高法关于格式管辖条款提示义务的规定](https://www.court.gov.cn/fabu/xiangqing/282651.html)。

- 【需律师确认】第 1 条、第 3.4 条、第 4 条末、第 6.1/6.4 条、第 7.2 条、第 8 条均属于与消费者有重大利害关系的格式条款。当前仅“使用即同意”，没有实际显著提示与说明路径；应确认哪些条款必须单独加粗、弹窗展示并取得明确确认。
- 【需律师确认】第 3.4 条把全额退款同时限制为“7 日内 + AI 调用不超过 10 次”，并以“原则上不退款”“长期不可用”等不确定表述保留裁量。固定期限订阅是否属于预付式服务、退款条件和未消费余额如何处理，以及数字化商品七日退货例外是否适用本服务，均需律师结合爱发电交易结构确认。
- 【需律师确认】第 4 条末和第 7.2 条对任何/严重违规均可终止且不退款，但没有违规分级、通知、纠正期、申诉或按未使用期限结算规则。需确认是否构成不合理加重消费者责任或排除退款权利。
- 【需律师确认】第 6.1 条“不承诺不间断”和第 6.4 条“最高不超过过去 12 个月实付费用”需要明确不适用于法律不得排除的责任，并核对故意、重大过失或人身损害等法定边界。
- 【需律师确认】第 8 条约定开发者所在地法院，但开发者主体和所在地尚未填写，也没有对管辖条款作独立显著提示。需确认该格式管辖条款的订入和效力。
- 【需律师确认】第 1 条的开发者主体、第 3.4 条退款渠道、第 9 条联系方式均不完整。应确认网络交易经营主体、售后、投诉、退款和个人信息权利请求所需披露项。

## 4. 草案已承诺但当前根本未实现

以下均不是措辞润色，而是上线前的实现/运营前提：
